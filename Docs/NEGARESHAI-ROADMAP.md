# نقشه راه نهایی NegareshAI

آخرین به‌روزرسانی: ۱۴۰۵/۰۵/۰۸ (2026-07-30)

وضعیت: **منتظر تأیید مالک محصول؛ اجرا شروع نشده است**

این سند ترتیب قطعی توسعه NegareshAI را براساس تصمیم‌های ثبت‌شده در
`NEGARESHAI-PRODUCT-SPEC.md` تعیین می‌کند. هر تغییری در هدف، ترتیب مراحل یا
معیار پایان نیازمند تأیید صریح مالک محصول است.

## ۱. هدف غیرقابل تغییر محصول

محصول فقط دو هدف اصلی دارد:

1. مدیریت هوشمند قراردادها
2. انطباق هوشمند اسناد

Identity، FileManager، اطلاعات پایه، دسترسی، RAG، OCR، گردش کار، اعلان،
گزارش و تنظیمات، زیرساخت پشتیبان این دو جریان هستند.

## ۲. ارزیابی خط مبنا

زیرساخت موجود قابل استفاده و باید حفظ شود:

- IdentityServer، UserManager، نقش و دسترسی مستقیم کاربر
- FileManager و نسخه‌های فایل
- SQL Server، tenant isolation، audit و soft delete اولیه
- OCR فایل PDF اسکن‌شده و embedding خصوصی BGE-M3/Chroma
- مدل اولیه سند، قرارداد، گروه سند، RuleSet، تطابق و تولید DOCX
- UI فارسی RTL و Docker Compose محلی
- migrationها و تست‌های موجود

موارد بالا به معنی تکمیل جریان محصول نیستند. فاصله‌های اصلی:

- نبود گروه قرارداد واقعی، گروه اصلی و template مؤثر
- ورود زودهنگام فایل آپلودشده به Vector Index پیش از تأیید
- نبود چرخه کامل استخراج، کارشناس، مدیر و انتشار RAG
- نبود چت پایدار و نسخه‌دار برای تولید/اصلاح قرارداد
- ناقص‌بودن معیارهای وزنی/حیاتی، آستانه گروه و اسناد طلایی
- نبود data-scope گروه قرارداد/سند در کنار مجوز عملیاتی
- استفاده‌نشدن از Pagination در UI و تجمیع چند موجودیت در یک صفحه
- وجود منطق مستقیم DbContext در برخی Controllerها

## ۳. قواعد معماری و Definition of Done مشترک

هیچ مرحله‌ای تکمیل نیست مگر اینکه همه موارد مرتبط زیر پاس شوند:

- Controller نازک؛ تمام use caseها با MediatR Command/Query/Handler
- نگاشت Entity/DTO با AutoMapper
- tenant scope از claim معتبر و fail-closed در Production
- مجوز عملیاتی API + دسترسی داده‌ای گروه
- AdminUser دارای تمام مجوزهای سامانه
- داده عملیاتی فقط از SQL/API؛ بدون گزینه کسب‌وکار hard-coded در UI
- ایجاد، ویرایش، فعال/غیرفعال، soft delete و restore متناسب با موجودیت
- ثبت Created/Modified/Deleted/Approved/Finalized با UserId و زمان
- Pagination سمت سرور برای تمام لیست‌ها، همراه جست‌وجو، فیلتر و مرتب‌سازی
- فرم و صفحه مستقل، فارسی RTL، responsive، دسترس‌پذیر و دارای empty/loading/
  error/forbidden states
- migration قابل ارتقا بدون حذف داده موجود
- unit، integration، authorization، tenant-isolation و acceptance test
- build تولیدی Backend/Frontend و health کانتینرها
- تست end-to-end معیار پایان مرحله
- به‌روزرسانی مستند وضعیت، commit و push کنترل‌شده

استاندارد Pagination:

- قرارداد پاسخ مشترک شامل `Items`, `PageNumber`, `PageSize`, `TotalCount`,
  `TotalPages`, `HasPreviousPage`, `HasNextPage`
- صفحه پیش‌فرض ۱ و اندازه پیش‌فرض ۲۰
- محدودیت اندازه در API و عدم واکشی همه رکوردها برای جدول‌های مدیریتی
- حفظ فیلتر، مرتب‌سازی و شماره صفحه در URL
- استفاده از کنترل Pagination مشترک و یکسان در تمام صفحات

## ۵. مراحل اجرایی

### M0 — تثبیت خط مبنا و معماری

هدف: آماده‌کردن کد موجود برای توسعه بدون ازبین‌بردن داده یا قابلیت سالم.

کارها:

1. ثبت snapshot دیتابیس، migrationها و تست‌های فعلی.
2. استخراج منطق P5 از Controller و انتقال به MediatR/AutoMapper.
3. تعریف پاسخ Pagination مشترک و Query options مشترک.
4. شکستن frontend تک‌صفحه‌ای به layout، route، component و feature module.
5. ایجاد design system سبک NegareshAI برای جدول، فرم، modal، pagination،
   status، error و permission state.
6. افزودن feature flag/migration strategy برای مهاجرت تدریجی داده موجود.

معیار پایان:

- هیچ regression در اسناد، قراردادها، Identity و FileManager وجود نداشته باشد.
- build و تست‌های موجود پاس شوند.
- هیچ Controller دامنه‌ای دسترسی مستقیم به DbContext نداشته باشد.
- shell جدید routeها را از منوی دسترسی Identity نمایش دهد.

### M1 — درخت دسترسی، نقش‌های سیستمی و Data Scope

هدف: هر قابلیت و هر گروه فقط برای کاربران مجاز قابل مشاهده و اجرا باشد.

کارها:

1. تکمیل درخت AccessMenu/AccessForm با والد، فرزند و actionهای مجزا.
2. ایجاد نقش‌های سیستمی حداقل:
   - AdminUser/Admin
   - کارشناس
   - مدیر امور قراردادها
3. مجوزهای مستقل مشاهده، ثبت، ویرایش، حذف، تأیید کارشناس، تأیید نتیجه
   انطباق، نهایی‌سازی قرارداد، نهایی‌سازی سند و انتشار RAG.
4. حفظ اعطا و رد مستقیم دسترسی کاربر؛ رد مستقیم بر نقش اولویت دارد.
5. مدل دسترسی نقش/کاربر به ContractGroup و DocumentGroup.
6. صفحه درختی مجوزها شبیه Healan با نمایش روشن والد هر action.
7. صفحه مستقل ماتریس/درخت دسترسی داده‌ای گروه‌ها.
8. AdminUser دارای همه مجوزها و همه گروه‌ها.

معیار پایان:

- کاربر فاقد منو، API مربوط را نیز با 403 دریافت کند.
- کاربر دارای action ولی فاقد group scope نتواند داده گروه را ببیند.
- اعطا/رد نقش و کاربر بدون login مجدد یا build frontend اثر قابل پیش‌بینی داشته
  باشد.
- تست نفوذ مجوز و tenant برای هر دو نوع گروه پاس شود.

### M2 — اطلاعات پایه و مدل دامنه مرجع

هدف: تمام گزینه‌های کسب‌وکار از داده‌های نسخه‌دار سازمان خوانده شوند.

کارها:

1. `ContractGroup` با عضویت چندبه‌چند قرارداد و یک `PrimaryGroup`.
2. ContractYear مستقل، پیشنهادشده از تاریخ شروع.
3. `ContractTemplate` متصل به گروه، نسخه، سال/بازه اثرگذاری و وضعیت فعال.
4. انتخاب قطعی template: گروه اصلی + تاریخ شروع + بالاترین نسخه فعال.
5. طرف قرارداد با ثبت inline برای کاربر دارای مجوز.
6. گروه سند با آستانه قبولی نسخه‌دار.
7. کاتالوگ معیار با عنوان یکتا، کد پایدار، وزن پیش‌فرض و قابلیت حیاتی.
8. اتصال معیارها به گروه با وزن/حیاتی/ترتیب مختص همان نسخه گروه.
9. چند سند طلایی نسخه‌دار با اولویت عددی.
10. تصمیم تعارض کارشناس با scope همان اجرا یا مرجع پایدار گروه.
11. CRUD، فعال/غیرفعال، soft delete، restore، audit و Pagination برای همه.
12. migration و تبدیل ایمن داده‌های اولیه موجود.

معیار پایان:

- هر زیرمنوی اطلاعات پایه صفحه مستقل و paginated داشته باشد.
- امکان تعریف گروه قرارداد، template سال ۱۴۰۵، گروه فولاد، معیارهای وزنی/
  حیاتی، آستانه و چند سند طلایی وجود داشته باشد.
- نبود template معتبر با پیام «گروه فاقد قالب معتبر است» fail-closed شود.
- نبود معیار و سند طلایی با پیام «گروه فاقد مرجع معتبر است» fail-closed شود.

### M3 — ورود اسناد، OCR، استخراج و چرخه اعتبار RAG

هدف: فایل ابتدا پردازش و بازبینی شود و فقط نسخه نهایی وارد دانش معتبر شود.

کارها:

1. ورودی DOCX، PDF متنی، PDF اسکن‌شده، JPG، PNG و TIFF.
2. بارگذاری چند تصویر برای یک نسخه سند.
3. شماره صفحه پیش‌فرض از ۱، جلوگیری از تکرار و امکان مرتب‌سازی قبل از ثبت.
4. عدم نمایش شماره صفحه برای PDF/DOCX.
5. محدودیت نوع/حجم، تشخیص MIME، malware hook و hash فایل.
6. OCR صفحه‌محور و نگهداری متن، confidence، صفحه و مختصات/بخش.
7. استخراج پیشنهادی سال، نسخه، شرکت، گروه، مبلغ، تاریخ، طرفین و بندها.
8. فرم بازبینی و اصلاح داده استخراج‌شده توسط کاربر.
9. lifecycle نسخه:
   `Uploaded → Extracted → ExpertReview → ManagerReview → Final/Rejected/
   Superseded`.
10. قرارداد تاریخی: تأیید کارشناس، سپس نهایی‌سازی مدیر امور قراردادها.
11. نگهداری متن استخراج‌شده پیش از تأیید، بدون ورود به Vector Index مجاز.
12. indexing فقط نسخه Final؛ unpublish نسخه منسوخ و حذف امن بردارها.
13. metadata اجباری tenant، document، version، groups، ACL و approval state.

معیار پایان:

- PDF، DOCX و سه تصویر نامرتب یک قرارداد تاریخی آپلود و مرتب شوند.
- OCR و استخراج فیلدها نمایش داده و اصلاح شوند.
- قبل از تأیید مدیر، RAG همان نسخه را بازیابی نکند.
- پس از تأیید کارشناس و مدیر، نسخه در RAG گروه مجاز قابل بازیابی باشد.
- کاربر سازمان/گروه دیگر هیچ chunk یا citation دریافت نکند.

### M4 — مدیریت هوشمند قرارداد و گفت‌وگوی نسخه‌دار

هدف: دو سناریوی تمدید قرارداد موجود و قرارداد کاملاً جدید اجرا شوند.

کارها:

1. `ContractConversation`, `Message`, `GenerationRun`, `DraftVersion`,
   `ChangeSet`, `Clarification` و snapshot منابع.
2. تاریخچه گفت‌وگو برای کاربر/سازمان و ادامه مکالمه.
3. انتخاب مبنا براساس شرکت + گروه اصلی + سال + بالاترین نسخه نهایی.
4. سؤال از کاربر در نتیجه مبهم یا چند قرارداد هم‌رتبه.
5. انتخاب template مؤثر گروه اصلی.
6. parsing فارسی تاریخ شمسی، مبلغ، درصد، شناسه، شرکت و بند.
7. اگر درصد و مبلغ قطعی متفاوت‌اند، نمایش محاسبه و سؤال اجباری.
8. RAG فقط از نسخه‌های Final، فعال، مجاز و snapshot‌شده.
9. قرارداد جدید بدون سابقه:
   - template معتبر گروه؛
   - کاتالوگ بندهای تأییدشده؛
   - پرسش‌وپاسخ فیلدهای الزامی؛
   - قرارداد گروه دیگر فقط با انتخاب صریح کاربر.
10. ثبت inline شرکت جدید با مجوز.
11. تولید بند با citation و اعلام بند ناشی از دستور مستقیم کاربر.
12. بررسی تعارض بند، تاریخ، مبلغ، تعهد، فسخ و حل اختلاف.
13. diff ساختاری و متنی و پیش‌نمایش DOCX/PDF.
14. هر اصلاح، نسخه immutable جدید؛ نسخه‌های ردشده قابل ممیزی.
15. گردش:
   `تأیید درخواست‌کننده → تأیید کارشناس → نهایی‌سازی مدیر`.
16. indexing قرارداد نهایی فقط پس از نهایی‌سازی مدیر.

معیار پذیرش A — تمدید شرکت فسا:

- قراردادهای ۱۴۰۳ و ۱۴۰۴ پشتیبانی شرکت فسا نهایی و در RAG باشند.
- کاربر قرارداد سال ۱۴۰۵ را مطابق آخرین نسخه ۱۴۰۴ درخواست کند.
- تاریخ ۱۴۰۵/۰۱/۰۱ تا ۱۴۰۵/۱۲/۲۹ اعمال شود.
- تعارض احتمالی افزایش ۲۵٪ با مبلغ ۲۹٬۰۰۰٬۰۰۰٬۰۰۰ سؤال شود.
- بند شورای حل اختلاف سازمان مدیریت بحران اضافه و منبع آن مشخص شود.
- template مؤثر سال ۱۴۰۵ استفاده شود.
- اصلاح محاوره‌ای، diff، سه تأیید و خروجی DOCX/PDF پاس شود.

معیار پذیرش B — قرارداد جدید عمران ماشین:

- شرکت در صورت نبود از داخل chat ثبت شود.
- کاربر گروه اصلی را انتخاب کند.
- اگر گروه سابقه ندارد، سامانه از template، بندهای تأییدشده و پاسخ کاربر
  استفاده کند.
- قرارداد گروه دیگر فقط با انتخاب صریح کاربر منبع شود.
- در نبود template تولید متوقف شود.
- قرارداد نگهداری ماشین‌آلات با تاریخ و مبلغ داده‌شده تولید، نسخه‌بندی و
  تأیید شود.

### M5 — انطباق هوشمند اسناد

هدف: امیدنامه جدید با قواعد و دانش معتبر گروه بررسی و پس از تأیید منتشر شود.

کارها:

1. انتخاب گروه سند و نسخه هدف.
2. snapshot آستانه، معیارها، وزن‌ها، حیاتی‌بودن، قواعد، اسناد طلایی و مدل.
3. بازیابی اسناد Final گروه براساس اولویت سند طلایی و ACL.
4. امتیاز:
   `Σ وزن معیارهای پاس‌شده ÷ Σ وزن معیارهای قابل اعمال × ۱۰۰`.
5. شکست معیار حیاتی همیشه نتیجه نامنطبق ایجاد کند.
6. نتیجه منطبق/نامنطبق/نیازمند بررسی با توضیح روش محاسبه.
7. citation صفحه و بند از سند هدف و منابع مرجع.
8. نمایش موارد منطبق، مفقود، اضافه، متفاوت و ممنوع.
9. پیشنهاد اصلاح و confidence.
10. تصمیم کارشناس روی یافته و نتیجه.
11. حل تعارض برای همان اجرا یا ثبت تصمیم مرجع گروه.
12. گزارش DOCX/PDF نسخه‌دار و قابل بازتولید.
13. اصلاح سند به‌عنوان نسخه جدید همان سند و اجرای مجدد.
14. مجوز جداگانه:
   - کارشناس نتیجه انطباق را تأیید می‌کند؛
   - مدیر امور قراردادها سند را نهایی و در RAG منتشر می‌کند.
15. نسخه ردشده یا صرفاً تأیید نتیجه‌شده وارد RAG نشود.

معیار پذیرش — امیدنامه فولاد دهدشت:

- گروه فولاد با آستانه، معیار وزنی، معیار حیاتی و چند سند طلایی تعریف شود.
- امیدنامه فولاد دهدشت آپلود و با منابع مجاز گروه بررسی شود.
- دلیل، امتیاز، شواهد صفحه‌ای و پیشنهاد اصلاح نمایش داده شود.
- نقض معیار حیاتی حتی با امتیاز عددی بالا نتیجه نامنطبق دهد.
- نسخه اصلاحی روی همان سند ثبت و دوباره بررسی شود.
- تأیید کارشناس به‌تنهایی آن را وارد RAG نکند.
- پس از نهایی‌سازی مدیر، نسخه در بررسی سند بعدی منبع قابل بازیابی باشد.

### M6 — گردش کار، ریسک و عملیات قرارداد

هدف: زیرساخت P5 با دامنه نهایی و معماری پروژه هم‌راستا شود.

کارها:

1. workflowهای قابل تنظیم سازمان و گروه قرارداد.
2. بررسی حقوقی، فنی، مالی، کارشناسی و مدیریتی.
3. نظر، درخواست اصلاح، رد، تأیید و delegation.
4. چک‌لیست ریسک تخصصی نسخه‌دار.
5. سررسید، تمدید، پرداخت، تضمین، تعهد و اعلان.
6. job امن و idempotent برای overdue/reminder.
7. داشبورد و گزارش tenant/group scoped.
8. صفحات مستقل paginated برای کارتابل، ریسک و عملیات.
9. انتقال کامل منطق از Controller به Application layer.

معیار پایان:

- کارتابل هر کاربر فقط وظایف مجاز او را نمایش دهد.
- تصمیم‌ها با UserId/زمان/نظر audit شوند.
- رویدادهای عقب‌افتاده و ۳۰ روز آینده از SQL واقعی محاسبه شوند.
- عملیات CRUD/soft-delete/restore و گزارش قابل دانلود پاس شوند.

### M7 — UX حرفه‌ای، کارایی و دسترس‌پذیری

هدف: دو جریان اصلی برای کاربر غیر‌فنی سریع، روشن و کم‌خطا باشند.

کارها:

1. wizard ورود قرارداد تاریخی و تصاویر چندصفحه‌ای.
2. chat workspace شامل منابع، سؤالات، محاسبات، diff و نسخه‌ها.
3. comparison workspace شامل معیارها، شواهد، امتیاز و تصمیم‌ها.
4. صفحه list/detail/form مستقل برای تمام اطلاعات پایه.
5. صفحه مستقل کاربران، نقش‌ها، درخت دسترسی و group scope.
6. صفحه مستقل هر گروه تنظیمات سازمان.
7. جدول استاندارد با search/filter/sort/pagination و URL state.
8. Persian date/number، keyboard navigation، focus، contrast و screen-reader.
9. modal فقط با X/عملیات صریح بسته شود؛ calendar داخل viewport reposition شود.
10. جلوگیری از double-submit، optimistic state کنترل‌شده و پیام خطای فارسی.
11. تست desktop/tablet/mobile و داده حجیم.

معیار پایان:

- تست کاربردپذیری سناریوهای فسا، عمران ماشین و فولاد بدون ورود مستقیم شناسه
  یا داده فنی انجام شود.
- تمام فهرست‌های بیش از ۲۰ رکورد pagination واقعی داشته باشند.
- هیچ صفحه تجمیعی چند موجودیت نامرتبط باقی نماند.
- منو و actionهای غیرمجاز نمایش داده نشوند.

### M8 — سخت‌سازی، کیفیت AI و انتشار

هدف: سامانه برای داده محرمانه و بهره‌برداری داخلی آماده شود.

کارها:

1. تست tenant، group ACL، direct deny و privilege escalation.
2. تست نشت RAG و prompt injection اسناد.
3. malware scan، file bomb، MIME spoofing و محدودیت منابع OCR.
4. encryption، secret management، TLS و redaction لاگ.
5. backup/restore SQL، FileManager و Vector Store.
6. retention و حذف هماهنگ SQL/file/vector.
7. observability، metric، trace، health/readiness و alert.
8. benchmark OCR فارسی، retrieval، citation، معیار حیاتی و تولید قرارداد.
9. تست load و Pagination با داده حجیم.
10. Docker خصوصی، runbook نصب، migration، rollback و disaster recovery.
11. پذیرش نهایی هر سه سناریوی مرجع در محیط شبیه Production.

معیار پایان:

- هیچ نشت بین سازمان یا گروه در تست‌ها وجود نداشته باشد.
- backup/restore واقعی و rollback migration آزمایش شود.
- سناریوهای فسا، عمران ماشین و فولاد از login تا خروجی/انتشار نهایی پاس شوند.
- نسخه release شماره‌دار، مستند و قابل نصب تحویل شود.
