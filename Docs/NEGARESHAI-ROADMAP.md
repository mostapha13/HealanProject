# نقشهٔ راه اجرایی NegareshAI

آخرین ارزیابی کد: 2026-07-28

این سند وضعیت واقعی پیاده‌سازی و ترتیب اجرای محصول را نگهداری می‌کند. وضعیت
هر قابلیت فقط براساس کد و تست موجود تعیین می‌شود، نه صرفاً وجود نام یک
endpoint یا توضیح در مستندات.

## تعریف وضعیت‌ها

- **تکمیل و تست‌شده:** مسیر اصلی قابلیت در Docker یا تست خودکار تأیید شده است.
- **زیرساخت اولیه:** اسکلت یا prototype وجود دارد، اما برای استفادهٔ واقعی
  سازمانی کامل نیست.
- **انجام‌نشده:** مدل دامنه یا جریان کاربردی قابل استفاده وجود ندارد.

## وضعیت واقعی فعلی

### تکمیل و تست‌شده

1. Compose مستقل NegareshAI شامل Web، API، AI/Chroma و SQL.
2. healthcheck و اجرای سالم چهار کانتینر NegareshAI.
3. اتصال به IdentityProvider و اعتبارسنجی JWT.
4. اتصال به FileManager و آپلود احراز‌شدهٔ PDF/DOCX.
5. ثبت حداقلی سند و نسخهٔ اول در SQL.
6. Swagger صحیح برای multipart upload.
7. سه تست رگرسیون API برای Swagger و اعتبارسنجی فایل.
8. استخراج متن پایه از PDF متنی و DOCX.
9. persistence پایهٔ Chroma در Docker.

### زیرساخت اولیه و غیرقابل تلقی به‌عنوان قابلیت نهایی

1. مدل‌های `Organization`، `Department`، `Document`، `DocumentVersion`،
   `ContractTemplate` و `Checklist` وجود دارند، اما ناقص‌اند.
2. API سند فقط upload، register و get-by-id دارد؛ فهرست، ویرایش، نسخهٔ جدید،
   بایگانی، حذف منطقی، مجوز سطح رکورد و audit ندارد.
3. frontend فقط صفحهٔ سادهٔ بارگذاری دارد و شناسهٔ سازمان در آن ثابت است.
4. استخراج متن PDF/DOCX پایه وجود دارد، ولی pipeline خودکار پس از upload،
   OCR، نگهداری صفحه/بند و وضعیت پردازش وجود ندارد.
5. chunking اولیه وجود دارد، ولی metadata صفحه، سازمان، سند، نسخه و مجوز را
   نگهداری نمی‌کند.
6. RAG index/search اولیه وجود دارد، اما embedding فعلی hash-based و غیرمعنایی
   است؛ isolation سازمانی، فیلتر مجوز و citation ندارد.
7. تولید DOCX فعلی فقط جایگزینی placeholder در قالب است؛ دستور طبیعی، بازیابی
   منابع، محاسبهٔ تغییرات، تولید بند حقوقی، پیش‌نمایش و تأیید انسانی ندارد.
8. مقایسهٔ قرارداد فعلی فقط diff پاراگراف‌های DOCX است؛ تغییرات عددی، تاریخی،
   حقوقی، شدت ریسک و PDF را پوشش نمی‌دهد.
9. compliance فعلی فقط وجود عین عبارت را بررسی می‌کند؛ موتور قواعد،
   پارامترهای نسخه‌بندی‌شده، تحلیل AI و شواهد صفحه‌محور ندارد.

### انجام‌نشده

1. دامنهٔ کامل قرارداد، طرفین، بندها، مبالغ، تاریخ‌ها، تعهدات و وضعیت‌ها.
2. گروه اسناد و انتساب چندگانهٔ سند به گروه.
3. مجموعه قواعد/پارامترهای نسخه‌بندی‌شده و قابل انتخاب.
4. اجرای تطابق و ذخیرهٔ یافته‌ها، شواهد و تصمیم کارشناس.
5. ایجاد/تمدید قرارداد با دستور فارسی و RAG خصوصی.
6. قالب و سربرگ سازمانی مدیریت‌شده و تولید نهایی DOCX/PDF.
7. گردش بررسی و تأیید انسانی.
8. کنترل دسترسی چندسازمانی در سطح داده، فایل و vector.
9. audit log محصول.
10. سررسید، تمدید، پرداخت، تعهد و اعلان.
11. داشبورد و گزارش مدیریتی واقعی.
12. تست‌های امنیت، isolation، integration و end-to-end کامل.

## اولویت اجرایی قطعی

تمام مراحل P0 تا P6 باید از الگوی Application/CQRS استفاده کنند:

- writeها به‌صورت MediatR Command/Handler
- readها به‌صورت MediatR Query/Handler
- نگاشت مدل‌ها با AutoMapper Profile
- Controllerهای نازک و فاقد منطق کسب‌وکار یا دسترسی مستقیم به DbContext
- تست ثبت Handlerها و اعتبار کامل AutoMapper configuration

### P0 — امنیت و پایهٔ دامنه

**وضعیت: تکمیل و تست‌شده در 2026-07-28**

هدف: قبل از ورود اسناد واقعی، مرز محرمانگی و مدل داده درست شود.

1. حذف OrganizationId ثابت از frontend و استخراج سازمان/کاربر از هویت معتبر.
2. اعمال tenant isolation و authorization در API و FileManager/RAG metadata.
3. طراحی موجودیت‌های Document، DocumentVersion، Contract، ContractParty،
   ContractClause، ContractValue، ContractDate و Attachment.
4. افزودن soft delete، confidentiality level، processing status و audit log.
5. migration و تست‌های authorization/isolation.

معیار پایان: کاربر نتواند با تغییر ID به سند سازمان دیگر دسترسی پیدا کند و
تمام عملیات مهم قابل ممیزی باشند.

نتیجهٔ اجرا:

- OrganizationId از قرارداد upload/register کلاینت حذف شد.
- tenant از claimهای معتبر سازمان استخراج می‌شود.
- fallback سازمان فقط در Development و از تنظیمات سرور مجاز است؛ Production
  بدون claim سازمان fail-closed است.
- read و soft delete سند با OrganizationId سرور فیلتر می‌شوند.
- مدل‌های قرارداد، طرفین، بندها، مبالغ، تاریخ‌ها، تعهدات و پیوست اضافه شدند.
- confidentiality، processing status، soft delete، membership و audit log
  اضافه شدند.
- migration `P0TenantSecurityAndContractDomain` ایجاد و در Docker اعمال شد.
- تست‌های نفوذ cross-tenant، soft delete و Production fail-closed پاس شدند.

### P1 — مدیریت واقعی سند و قرارداد

**وضعیت: تکمیل و تست‌شده در 2026-07-28**

1. CRUD و فهرست/جست‌وجوی اسناد و قراردادها.
2. ثبت نسخهٔ جدید بدون بازنویسی نسخهٔ قبلی.
3. صفحات فهرست، جزئیات، ویرایش، نسخه‌ها و بایگانی.
4. مدیریت طرفین، مبلغ، تاریخ‌ها، وضعیت و مسئول قرارداد.
5. دانلود امن و نمایش فایل‌ها.

معیار پایان: یک سازمان بتواند قرارداد را از ایجاد تا نسخه‌بندی و بایگانی
بدون قابلیت AI مدیریت کند.

نتیجهٔ اجرا:

- فهرست صفحه‌بندی‌شده و جست‌وجو/فیلتر اسناد با tenant isolation اضافه شد.
- ویرایش مشخصات سند و ثبت audit اضافه شد.
- ثبت نسخهٔ جدید در FileManager بدون بازنویسی نسخهٔ قبلی اضافه شد.
- صفحهٔ اصلی فهرست و جست‌وجوی سند و نمایش تعداد نسخه‌ها را ارائه می‌کند.
- CRUD قرارداد با طرفین، مبلغ/ارز، تاریخ‌ها، وضعیت و مسئول داخلی اضافه شد.
- جزئیات سند، تاریخچهٔ نسخه‌ها، بایگانی/بازیابی و دانلود امن از طریق proxy
  احراز‌شدهٔ API اضافه شد.
- UI فهرست و فرم قرارداد، ویرایش سند، ثبت نسخه، بایگانی/بازیابی و دانلود امن
  تکمیل شد.
- تست‌های backend 12/12، build تولیدی frontend و سناریوی کامل Docker/SQL
  شامل ایجاد/ویرایش/جست‌وجو/بایگانی قرارداد و چرخهٔ سند پاس شدند.

### P2 — pipeline خصوصی پردازش و RAG معتبر

**وضعیت: در حال انجام — برش pipeline امن در 2026-07-28 تکمیل و تست شد**

1. job خودکار پس از upload: دریافت فایل، استخراج، OCR در صورت نیاز، chunk و
   index.
2. ثبت صفحه، بند، سند، نسخه، سازمان و ACL روی هر chunk.
3. جایگزینی embedding آزمایشی با embedding فارسی/چندزبانهٔ محلی و تست کیفیت.
4. بازیابی همراه با فیلتر قطعی tenant/permission.
5. citation صفحه‌محور و ثبت نسخهٔ مدل/prompt.

معیار پایان: جست‌وجوی معنایی فارسی، منبع درست و مجاز را همراه با صفحه برگرداند
و هیچ داده‌ای از سازمان دیگر بازیابی نشود.

نتیجهٔ برش اول:

- pipeline یکپارچهٔ استخراج PDF/DOCX، chunk ساختاریافته و index اضافه شد.
- metadata اجباری `organizationId`، `documentId`، `versionId`، صفحه، بخش و
  شماره chunk در Chroma ذخیره می‌شود.
- index مجدد یک نسخه idempotent است و chunkهای قبلی همان نسخه را جایگزین
  می‌کند.
- جست‌وجو tenant-scoped است، فیلتر اختیاری اسناد دارد و citation شامل سند،
  نسخه، صفحه و بخش برمی‌گرداند.
- upload و ثبت نسخه جدید در API به پردازش خصوصی متصل شد و وضعیت
  Processing/Ready/Failed و audit ثبت می‌شود.
- endpoint پردازش مجدد دستی اضافه شد.
- تست Docker جداسازی دو سازمان و الزام tenant context پاس شد؛ تست‌های backend
  نیز 12/12 پاس هستند.
- باقی‌ماندهٔ P2: OCR فایل اسکن‌شده، embedding معنایی فارسی/چندزبانهٔ محلی
  به‌جای hash prototype، ACL فراتر از tenant، تست کیفیت بازیابی و اجرای کامل
  stack با imageهای جدید.

Checkpoint مدل فارسی/اعداد در 2026-07-29:

- `BAAI/bge-m3` به‌عنوان مدل پیشنهادی انتخاب و از تنظیم tenant-scoped
  `ai/embedding.model` خوانده می‌شود.
- collectionهای Chroma به‌ازای model ID جدا هستند.
- normalization ارقام فارسی/لاتین و boost تطابق دقیق عدد برای مبلغ، تاریخ،
  درصد و شناسه اضافه شده است.
- وابستگی Torch به wheel نسخه CPU محدود شده است؛ build و smoke test نهایی
  image CPU اولین کار جلسه بعد است.

### P3 — مدیریت دانش و موتور تطابق اسناد

1. گروه‌های اسناد مانند «فولادی».
2. RuleSet، Rule، Parameter و نسخه/اعتبار زمانی آن‌ها.
3. انتخاب مبنا: گروه، قواعد، سند مرجع یا حالت ترکیبی.
4. ComparisonRun و Finding با وضعیت، شدت، دلیل، شاهد و confidence.
5. تأیید/رد/اصلاح یافته توسط کارشناس.
6. گزارش DOCX/PDF قابل ممیزی.

معیار پایان: سناریوی امیدنامهٔ گروه فولادی و مقایسه با شرکت B به‌طور کامل
قابل اجرا باشد.

### P4 — ایجاد و تمدید هوشمند قرارداد

1. مدیریت قالب و سربرگ رسمی هر سازمان.
2. انتخاب قرارداد مبنا و منابع مجاز RAG.
3. تبدیل دستور فارسی به ChangeSet ساختاریافته.
4. اعتبارسنجی تاریخ، مبلغ، ارز و درصد و نمایش محاسبات.
5. تولید/اصلاح بند با citation و بررسی تعارض.
6. پیش‌نمایش diff و تأیید انسانی.
7. تولید DOCX/PDF و ثبت به‌عنوان نسخهٔ پیش‌نویس AI.

معیار پایان: سناریوی تمدید قرارداد شرکت A با تاریخ‌های ۱۴۰۵، افزایش ۲۵ درصد،
مبلغ تعیین‌شده و بند مذاکره با سربرگ شرکت اجرا شود.
